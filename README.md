# YandexGPT: извлечение сущностей из юридических документов

Docker-окружение для домашнего задания по NER. Интерфейс — JupyterLab.
Базовый образ: официальный Jupyter Docker Stacks с датированным тегом.
Дополнительные библиотеки перечислены в `requirements.txt`; диапазоны версий
не являются lock-файлом и могут разрешаться иначе при будущей пересборке.

## Настройка перед первым запуском

Требуются запущенный Docker Desktop и Docker Compose.

Сначала подготовьте `.env` в корне проекта. При первом клонировании:

```bash
cp .env.example .env
chmod 600 .env
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Вставьте сгенерированное значение в `JUPYTER_TOKEN` внутри `.env`.
Если локальный `.env` уже подготовлен, проверьте его вместо копирования
шаблона. Перед запуском контейнера обязательно заполните в `.env` две
переменные для доступа к YandexGPT.

```dotenv
YANDEX_API_KEY=
YANDEX_FOLDER_ID=
```

- `YANDEX_API_KEY` — секретный API-ключ сервисного аккаунта Yandex Cloud.
- `YANDEX_FOLDER_ID` — идентификатор каталога Yandex Cloud, для которого
  настроен доступ к YandexGPT.

`YANDEX_MODEL_URI` можно оставить пустым. Для пробного запроса тогда
используем `gpt://<YANDEX_FOLDER_ID>/yandexgpt`. Сохраните файл.

## Запуск

Запустите контейнер после сохранения заполненного `.env`:

```bash
docker compose up -d --build
docker compose ps
```

`JUPYTER_PORT` в `.env` задаёт порт в адресе браузера. По умолчанию
это [localhost:8888](http://localhost:8888/lab). Если у вас
`JUPYTER_PORT=8890`, откройте [localhost:8890](http://localhost:8890/lab).
Порт доступен только на локальном компьютере.

На странице входа в поле **Password or token** вставьте значение
`JUPYTER_TOKEN` из `.env`. В ячейках ноутбука порт задавать не нужно.

Папки `notebooks/`, `data/` и `outputs/` сохраняются на компьютере и доступны
в Jupyter. Удаление контейнера не удаляет эти файлы.

В ноутбуке `notebooks/01_schema.ipynb` можно проверить семь эталонов из
`data/annotations/`. Схема импортируется из `legal_ner/schema.py`.
`Extraction` описывает ответ модели, а `AnnotatedDocument` добавляет
`document_id`, который берётся из имени исходного файла. После изменения
Compose-конфигурации выполните `docker compose up -d`, чтобы подключить модуль
к уже запущенному окружению.

Проверка доступности настроек в ячейке без вывода ключа:

```python
import os

assert os.environ.get("YANDEX_API_KEY"), "Заполните YANDEX_API_KEY в .env"
assert os.environ.get("YANDEX_FOLDER_ID"), "Заполните YANDEX_FOLDER_ID в .env"
print("Настройки YandexGPT доступны")
```

Compose передаёт значения из `.env` при создании контейнера. Внутри
ноутбука их можно читать через `os.environ`. Для первого запуска достаточно
один раз выполнить команду выше после заполнения файла.

Остановка:

```bash
docker compose down
```

## Секреты и публикация

`.env` исключён из Git; в репозитории хранится только `.env.example`.
Docker получает при сборке только Dockerfile и requirements.txt: секреты
не попадают в образ. В контейнер передаются переменные окружения, а сам
файл `.env` не монтируется. Не выводите ключи и всё окружение в ноутбуках;
перед публикацией проверьте сохранённые выводы ячеек.

На этом этапе API-клиент и NER-пайплайн ещё не реализованы.

## Корпус юридических документов

Источник: [TryDotAtwo/russian-legal-ner](https://huggingface.co/datasets/TryDotAtwo/russian-legal-ner)
на Hugging Face. Корпус содержит судебные тексты на русском языке и span-разметку
NER. Это судебные документы, а не специально подобранные договоры с реквизитами.
Загружаются целиком train, validation и test, без фильтрации или обрезки текста.
Версия зафиксирована: `d23f5380ccbd0b14c27efb8c9b7280d13cb4b85a`.
В этой версии 97 668 записей: train — 73 734, validation — 13 934, test — 10 000.
Объём исходных Parquet-файлов — около 175 МБ; для распакованных TXT требуется
дополнительное место. API YandexGPT для загрузки не используется.

Из корня проекта выполните:

```bash
docker compose build jupyter
docker compose run --rm -T --no-deps jupyter python -u < scripts/download_corpus.py
```

Если нужны только исходные Parquet без экспорта в TXT, достаточно Python 3
на компьютере (дополнительные библиотеки не требуются):

```bash
python3 scripts/download_corpus.py --download-only
```

Скрипт использует `pyarrow` из requirements.txt. Существующие исходные файлы
повторно не скачиваются; каталог и TXT пересоздаются. Незавершённая загрузка
остаётся в `.part` и при следующем запуске начинается заново.

Результаты в `data/raw/russian-legal-ner/` (доступны также в Jupyter):

- `train.parquet`, `validation.parquet`, `test.parquet` — оригинальные данные,
  включая колонку `spans` с исходной разметкой.
- `texts/<split>/<split>_<номер>.txt` — полный текст каждой строки корпуса
  в UTF-8, без нормализации и обрезки.
- `catalog.csv` — идентификатор, часть корпуса, номер строки, длина, путь
  к TXT относительно каталога корпуса и первые 300 символов для просмотра.
- `manifest.json` — версия, URL, размеры, SHA-256 файлов и число текстов.
- `SOURCE_README.md` — исходная карточка датасета.

Для ручного отбора просмотрите `catalog.csv` и соответствующие TXT, затем
сохраните идентификаторы выбранных примеров. Автоматический отбор не выполняется.
Исходная NER-разметка не считается эталоном для нашей схемы реквизитов и сроков.

В карточке источника лицензия указана как `other`; авторство принадлежит
первоначальным авторам. Корпус хранится локально в исключённой из Git папке
`data/raw/`; скрипт и инструкции позволяют воспроизвести загрузку без публикации
копии корпуса в репозитории.

## Правила разметки судебных актов

Цель разметки — извлечь сведения о сторонах, датах, денежных суммах и сроках
обязательств. Суммы и даты сохраняем строками в исходном виде. Принимаем
записи цифрами, прописью и в смешанном виде. Поле `currency` из разметки исключаем.

### Документ

Для каждого исходного TXT создаём один эталонный JSON в `data/annotations/`.

- `document_id` — имя TXT без расширения, например `"test_002610"`.
  Идентификатор подставляем из имени файла.
- `case_number` — номер дела из текста акта, например `"5-54/2013"`. Если
  номер отсутствует или скрыт, указываем `null`.
- `act_type` — вид акта, например `"решение"`, `"заочное решение"`,
  `"определение"` или `"постановление по делу об административном правонарушении"`.
  Если вид акта определить нельзя, указываем `null`.

TXT со смешанными фрагментами разных дел отмечаем в
`data/annotations/excluded_documents.json` со статусом `mixed_cases` и
пояснением. Такие документы исключаем из основной проверки.

### Стороны и реквизиты

В `parties` размечаем стороны дела, участников описанных договоров и
соглашений, а также получателя платежа, если приведены его реквизиты.
Каждый объект описывает одного участника.

| Поле | Что записываем |
| --- | --- |
| `name` | Название организации или имя человека из акта. Если имя скрыто, ставим `null`. |
| `role` | Роль в деле, договоре или платеже, например `"истец"`, `"ответчик, арендатор"` или `"получатель штрафа"`. Роль может следовать из конструкции «по иску А к Б». Если определить её нельзя, записываем `"роль не указана"`. |
| `inn` | ИНН этого участника строкой из цифр. Если реквизит отсутствует или скрыт, ставим `null`. |
| `kpp` | КПП этого же участника строкой из цифр. Если реквизит отсутствует, скрыт или неприменим, ставим `null`. КПП необычной длины сохраняем как в источнике. |
| `evidence` | Фрагмент акта, подтверждающий участника, его роль и принадлежность реквизитов. Если сведения разнесены по тексту, выбираем наиболее подтверждающий фрагмент. |

Реквизиты получателя штрафа записываем отдельно от реквизитов того, кто
должен его уплатить.

### Даты

В `dates` включаем дату судебного акта, даты заключения и регистрации
договоров или соглашений, начала и окончания их действия и другие даты,
относящиеся к делу или обязательствам сторон. В `kind` указываем событие,
к которому относится дата.

В `date` копируем исходное выражение. Например, `25 февраля 2013 года`
сохраняем как `"25 февраля 2013 года"`, а `25.02.2013 г.` — как
`"25.02.2013 г."`. Разделители, название месяца и сокращения сохраняем.

Если дата явно скрыта, например «договор от `<ДАТА2>`», создаём запись
с `date: null` и цитатой. Если дата вообще не упомянута, запись не создаём.

### Денежные суммы

В `amounts` включаем все явно указанные денежные значения из всего акта.
Это цены, долги, платежи, пени, штрафы, госпошлины, тарифы и суммы из описания
обстоятельств. Например, в `test_002610` размечаем штраф в 700 000 рублей,
изъятые 30 950 рублей и 100 рублей выигрыша при проверке терминала.

- В `amount` копируем денежное выражение со всеми разделителями и
  сокращениями, включая обозначение валюты, если оно входит в запись.
  Примеры: `"4 470 рублей 26 копеек"`, `"18.150 рублей"`,
  `"семьсот тысяч рублей"`. Сумму с дублем прописью записываем одним
  фрагментом, например `"700 000 (семьсот тысяч) рублей"`.
- Если валюта указана только в заголовке таблицы, в `amount` копируем
  значение ячейки, например `"2753,14"`. Заголовок включаем в `evidence`,
  если его можно привести вместе со значением одной цитатой.
- В `kind` указываем назначение суммы. Для тарифа указываем также единицу,
  например `"тариф за километр сверх лимита"`.
- Один денежный факт размечаем один раз. Одинаковые значения сохраняем
  отдельно, если они относятся к разным назначениям, периодам или
  участникам. Заявленная и взысканная суммы — две записи, даже если
  значения совпадают.
- Если в расчёте и резолютивной части указаны разные суммы, сохраняем обе
  и различаем их по `kind`. Итоги и скрытые суммы самостоятельно не вычисляем.
- Если сумма упомянута, но скрыта как `***` или `<ОБЕЗЛИЧИНО>`, ставим
  `amount: null` и сохраняем исходное упоминание в `evidence`. Если
  денежный факт отсутствует, запись не создаём.
- Проценты, даты, номера документов, расстояния и другие неденежные числа
  в `amounts` не входят.

### Сроки обязательств

В `deadlines` включаем сроки исполнения обязательств, например оплаты,
поставки, представления документов или уплаты штрафа. Сроки обжалования
и фактическую продолжительность просрочки не включаем.

- Для относительного срока в `value` записываем целое число, в `unit` —
  единицу, а в `start_event` — событие начала отсчёта, если оно указано.
  Например, для «в течение 5 рабочих дней со дня принятия банком платёжного
  документа» указываем `5`, `"рабочие дни"` и
  `"принятие банком платёжного документа"`.
- Для конкретной крайней даты заполняем `due_date` строкой из источника.
  Если в графике отдельно указаны день оплаты и крайний день зачисления,
  для обязательства по зачислению берём значение из его колонки. Если
  день приведён отдельно от месяца и года, копируем день как в ячейке,
  указываем месяц и год в `kind` и приводим строку графика в `evidence`.
- Для повторяющегося срока сохраняем периодичность в `value` и `unit`,
  точное правило описываем в `kind` и подтверждаем цитатой. Например,
  для ежеквартальной оплаты указываем `1` и `"квартал"`, а в `kind`
  уточняем «не позднее 20-го числа последнего месяца квартала».
- Если поле срока неприменимо или значение скрыто, указываем `null`.

### Цитаты и оценка

В каждой записи `parties`, `dates`, `amounts` и `deadlines` поле `evidence`
содержит фрагмент исходного текста. При сравнении обычные и неразрывные
пробелы считаем равнозначными, переносы строк можно сводить к пробелам.
Пунктуацию и разделители внутри сумм и дат сохраняем. Цитата может быть
короче или длиннее эталонной, если она есть в источнике и подтверждает
тот же факт.

Формат JSON проверяем схемой Pydantic. Ключи обязательны. Значение `null`
допускается в полях, предусмотренных схемой. Если для группы нет ни одной
записи, возвращаем пустой список `[]`.

Для суммы и даты сверяем исходную запись и факт, к которому она относится.
Для реквизитов сверяем значение и участника. Для срока проверяем действие,
длительность или крайнюю дату, а также событие начала отсчёта, если оно
указано. «Основной долг» и «основная задолженность» считаются совпадением,
если речь об одном факте.

## Сравнение с эталонами на шаге 6

Первая таблица показывает объём разметки и число точных совпадений.
Одна строка относится к одному документу и одной группе фактов.
В таблицу входят завершённые ответы, которые прошли проверку схемы.

| Колонка | Что показывает |
| --- | --- |
| Документ | Идентификатор исходного судебного акта. |
| Группа | Стороны, даты, суммы или сроки. |
| Эталон | Количество записей этой группы в ручной разметке. |
| Модель | Количество записей этой группы в ответе YandexGPT. |
| Точных пар | Сколько записей совпало по всем полям после нормализации пробелов. Поле `evidence` проверяем отдельно. Каждая запись участвует максимум в одной паре. |

Точное сравнение учитывает регистр букв, пунктуацию и формулировки ролей
или назначений. В `validation_002682` имя ответчика и его поля совпали.
Название истца начинается с прописной «А» в эталоне и со строчной «а»
в ответе, поэтому автоматически засчитана одна точная пара из двух.
Обе стороны при этом опознаны по смыслу. Записи без точной пары
просматриваем во второй таблице, чтобы отличить другую формулировку
от пропуска или ошибки в извлечённом факте.

## Проверка отсутствующих данных

На шаге 7 отправляем в YandexGPT `test_003541.txt`, решение о расторжении
брака. В акте нет денежных сумм и сроков исполнения обязательств.
Месячный срок обжалования относится к процессуальным срокам и исключается
по правилам разметки.

Для этого теста достаточно частичного эталона `{"amounts": [], "deadlines": []}`.
Его задаём вручную в ноутбуке и используем локально после запроса.
Стороны и даты в этой проверке не оцениваем. Пустой список означает,
что фактов этого типа в тексте нет. Если факт упомянут, а его значение
скрыто, сохраняем запись с `null` внутри списка.

## Проверка на OCR-шум

На шаге 8 сравниваем два ответа YandexGPT на один судебный акт
`test_006753`. Для чистого прогона используем исходный TXT со шага 5.
Для второго прогона отправляем копию, в которой три кириллические
буквы заменены похожими латинскими. Числа и параметры запроса сохраняем.
На шаге 8 выполняем один новый запрос.

Колонка **«Найден в чистом прогоне»** показывает, есть ли подходящая
запись в ответе модели на исходный акт. Колонка **«Найден после OCR»**
показывает то же для ответа на зашумлённую копию. `False` означает,
что проверка не нашла подходящей записи в ответе модели. Например,
в исходном акте указаны 10 дней аренды, а модель в чистом прогоне
вернула `deadlines: []`.

| Чистый прогон | После OCR | Что наблюдаем |
| --- | --- | --- |
| `True` | `True` | Факт найден в обоих ответах. |
| `True` | `False` | Факт найден только в ответе на исходный текст. |
| `False` | `False` | Факт пропущен в обоих ответах. |
| `False` | `True` | Факт найден только в ответе на зашумлённый текст. |

Результат сохранённой проверки:

| Факт | Найден в чистом прогоне | Найден после OCR |
| --- | --- | --- |
| Дата акта — 25 февраля 2013 года | `True` | `True` |
| Срок аренды — 10 дней | `False` | `True` |
| Тариф — 2 рубля за километр | `False` | `False` |

Для поиска фактов заменённые в эксперименте буквы считаем равнозначными.
При проверке цитат нормализуем только пробелы и сверяем цитату с тем
текстом, который получила модель. В исходном прогоне не нашлись 7 цитат,
в зашумлённом — 11. Результаты двух запросов показывают различия между
ответами. Чтобы оценить влияние шума на качество, нужны повторные прогоны
на нескольких актах.
